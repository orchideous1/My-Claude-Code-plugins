# 工作流定位

本阶段属于 `arch` 工作流的 **MODEL**。CONNECT 已明确关系；本阶段将理解综合为架构模型，写入 `.claude/state/sessions/<id>/architecture.md`。

**离开本阶段的验收标准**：
- `architecture.md` 已按 required 章节完成；
- 模型像“资深工程师带新人读代码”的 walkthrough，而非中性 API 参考；
- 开放问题、可读性已自检；
- 如稳固 → 标记 DONE；如有缺口 → 返回 DRILL，关系不清 → 返回 CONNECT，范围错误 → 返回 SCOPE。

## 输出格式与操作

将理解综合到 `.claude/state/sessions/<id>/architecture.md`。

产物定位：一篇“资深工程师带新人读代码”的架构 walkthrough，而不是中性的 API 参考手册。

## 必须包含的章节

1. **开篇价值定位**
   - 用 1-2 段话讲清楚：这个模块/系统是什么、解决了什么痛点、为什么值得读。
   - 点明读者读完能得到的 3 个核心认知。

2. **鸟瞰结构**
   - 目录/模块边界、入口点、关键文件。
   - 用 Mermaid 或文本图呈现整体组件关系。
   - 首次引用核心文件时附带 GitHub 永久链接（如果已知 commit/tag）。

3. **核心组件逐一解读**
   - 只选最重要的 5-8 个抽象，不要罗列所有类和方法。
   - 每个抽象包含：
     - 一句话职责；
     - 关键代码片段，放在 `<details>` 可折叠块中（保留核心逻辑，删除日志和次要分支）；
     - 1-3 行“这段代码在做什么”的点评；
     - 设计亮点或潜在坑点（作者点评）。

4. **数据流与控制流**
   - 用分步骤文字 + Mermaid 序列图描述关键流程。
   - 对于涉及循环、状态机或批量调度的逻辑，必须给出一个带具体参数值的运行示例。

5. **关键决策与权衡**
   - 解释“为什么这样设计”。
   - 穿插“作者点评”：巧妙之处、边界、风险、如果改进会怎么改。

6. **接口契约（以使用方式呈现）**
   - 不讲中性类型签名，而讲“如果你想调用/扩展它，应该调用什么、参数含义、常见坑点”。

7. **开放问题**
   - 仍不清楚、未验证或值得后续深挖的地方。

## 文风要求

- 有观点、有语气，允许使用“写得非常清爽”“这里很巧妙”“坦诚说这里还有提升空间”等工程师口语。
- 用中文撰写；文件名、类名、方法名保留英文原样。
- 抽象机制必须落地到代码行号或代码片段，不能只停留在概念层。
- 复杂算法必须配以具体参数示例，而不是纯符号描述。

## 写完后检查缺口

- 是否还有事实缺口？→ 回到 DRILL
- 关系是否清楚？→ 回到 CONNECT
- 范围是否错误？→ 回到 SCOPE
- 是否像 walkthrough 而非参考手册？如不像，重写开篇和组件解读章节
- 如稳固且可读 → 标记 DONE
